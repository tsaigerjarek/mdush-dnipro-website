# Правила роботи Google Antigravity

## Призначення

Цей repository містить офіційний сайт МДЮСШ Дніпро.

Google Antigravity працює з уже існуючим проєктом: аналізує, вносить контрольовані зміни, перевіряє їх і готує до review. Він не повинен створювати сайт заново або змінювати архітектуру без окремого рішення.

## Мова та стиль

- Спілкування, документація, назви організаційних матеріалів, коментарі та повідомлення комітів — українською мовою.
- Писати стисло, зрозуміло та без припущень.
- Публічні тексти готувати лише на основі підтверджених джерел.

## Перед будь-якими змінами

1. Прочитати цей файл `AGENTS.md`.
2. Прочитати relevant workspace rules у `.agents/rules/` (зокрема `mdush-project-governance.md`).
3. Прочитати relevant skills у `.agents/skills/`.
4. Перевірити `package.json` та фактичні scripts.
5. Перевірити чинні файли, конфігурації та структуру repository.
6. Перевірити `git status` і поточну гілку (`current branch`).
7. Сформулювати root cause, чіткий scope та acceptance criteria.

Не вважати створення структури або файлів доказом готовності функціоналу, інтеграції чи deployment.

## Гілки та погодження

- Усі зміни виконувати в окремій гілці (`feature branch`); у `main` безпосередньо не працювати.
- Один етап / задача = одна окрема гілка (`feature/...`, `fix/...`, `content/...`).
- Для змін створювати Pull Request, за замовчуванням Draft Pull Request.
- Злиття (merge) в `main`, публікація сайту та production deployment — лише після явного погодження власника проєкту.
- Не створювати та не змінювати GitHub Actions, автоматичне розгортання або конфігурації хостингу без окремого доручення.
- Заборонено виконувати деструктивні дії з Git (force-push, reset, stash drop/pop, branch deletion) без прямого дозволу.
- Не використовувати `git add .` у dirty worktree; додавати (stage) лише конкретні цільові файли поточної задачі.

## Мінімальне втручання та збереження архітектури

- Перед реалізацією знайти першопричину (root cause).
- Не робити широкий opportunistic refactor, якщо задачу можна вирішити локально в межах scope.
- Не додавати dependencies без обґрунтування та узгодження.
- Не змінювати framework (Astro), routes або architecture deployment без окремого рішення.

## Достовірність контенту та персональні дані

- Заборонено вигадувати юридичні факти, контакти, тренерський склад, вихованців, результати матчів, документи, регалії чи статистику.
- Непідтверджені дані позначати як `TODO: потребує підтвердження — <що саме перевірити>`.
- Не підміняти офіційні джерела припущеннями чи тестовими макетами, що виглядають як факти.
- Суворо заборонено публікувати персональні, медичні або приватні дані дітей: повні дати народження (день/місяць), адреси, телефони, email, школи, дані батьків, внутрішні оцінки тренерів.
- Для вихованців дозволено лише підтверджене публічне ім'я (`publicName`), рік народження (наприклад, `2012 р.н.`), вікова категорія, позиція та підтверджені досягнення.

## Джерела істини та медіа

- GitHub є єдиним джерелом істини для програмного коду, структури сайту, конфігурацій без секретів, погоджених текстів, оптимізованих публічних матеріалів, метаданих і журналу змін.
- Великі оригінали фото/відео, робочі матеріали, приватні фото/відео та непублічні документи до GitHub не додавати.
- Фото й відео дітей не додавати автоматично. Для публікації потрібні підтверджене право використання (`photoApprovedForPublicUse === true`), офіційна згода батьків, редакційна перевірка та дозвіл відповідальної особи. За відсутності дозволу використовувати нейтральний плейсхолдер («Фото готується»).
- Усі публічні фотографії дітей повинні бути повністю очищені від метаданих EXIF (геолокація, дата).

## Спортивні напрями та правила дизайну

- Три спортивні напрями МДЮСШ (футбол, настільний теніс, черліденг) мають однаковий статус та однакове візуальне представлення.
- Заборонено створювати штучну ієрархію між видами спорту або називати будь-який із них «основним», «провідним» чи «другорядним».
- Не використовувати декоративну нумерацію (01, 02, 03) та зайві службові eyebrow-мітки у публічному UI.
- Забезпечувати повну адаптивність (mobile-first, без горизонтального скролу), розмір touch-target не менше 44–48 px, доступність за WCAG (контрастність, семантика, навігація з клавіатури).

## Дані та секрети

- Не зберігати паролі, токени, API-ключі, облікові дані, персональні або медичні дані дітей.
- Не додавати приватні документи або матеріали з невизначеними правами використання.
- Локальні секрети зберігати у виключеному з Git файлі `.env`; production-секрети — у захищеному сховищі платформи.
- Заборонено вставляти секрети у код, документацію, коментарі, Issues чи Pull Requests.

## Workspace Isolation

- За замовчуванням працювати тільки в корені поточного repository та його підкаталогах.
- Не читати і не використовувати без прямої вказівки файли поза поточним workspace (інші репозиторії, `~/.gemini/`, `~/.codex/`, Desktop, Documents, Downloads).
- Сторонні AI memory directories не є джерелом істини.
- Джерела істини: поточний working tree, Git history поточного repository, `AGENTS.md`, `.agents/rules/`, `.agents/skills/` та підтверджені джерела.

## Перевірка перед Draft PR / завершенням

Перед підготовкою звіту чи PR обов'язково виконати:
1. `npm test` (контроль якості: перевірка типів, збірка 15 сторінок, маршрути, SEO-метадані, зображення, відсутність стороннього JS).
2. `git diff --check` (відсутність небажаних пробілів та синтаксичних конфліктів).
3. `git status -sb` (перевірка стану гілки та змінених файлів).
4. Перевірити відсутність секретів, персональних і медичних даних.
5. Переконатися, що `main` не змінювався напряму і не було запуску несанкціонованого deployment.
