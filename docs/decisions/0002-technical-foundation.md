# ADR-0002: Технічна основа першої версії сайту

- Статус: запропоновано
- Дата: 2026-07-29
- Рішення набирає чинності лише після погодження та злиття цього Pull Request.
- Цей документ не дозволяє створювати код, вмикати GitHub Pages, налаштовувати домен або публікувати сайт.

## Контекст

МДЮСШ Дніпро потрібен легкий офіційний сайт для публічного представлення закладу та подальшої заявки Google Workspace for Education. Сайт має швидко працювати на телефонах і за нестабільного мобільного інтернету, не збирати персональні дані дітей та не потребувати окремої бази даних чи складної адмінпанелі.

Погоджені межі MVP визначені в `0001-mvp-boundaries.md`. Цей документ уточнює технічний спосіб їх реалізації.

## Рішення

### Генератор і мова

- Astro у режимі статичної генерації;
- TypeScript у строгому режимі;
- готовий сайт складається зі статичних HTML, CSS, JavaScript та оптимізованих зображень;
- клієнтський JavaScript додається лише там, де без нього неможлива потрібна взаємодія;
- React, Vue та інші UI-фреймворки не додаються до MVP без окремого обґрунтування.

### Стилі та компоненти

- звичайний CSS із дизайн-токенами через CSS-змінні;
- локальні повторно використовувані компоненти Astro;
- без важкої бібліотеки компонентів;
- без анімаційних бібліотек;
- системні шрифти або один локально розміщений вебшрифт після перевірки ліцензії та швидкості.

### Сторінки MVP

Публічна навігація першої версії містить шість основних розділів:

1. Головна.
2. Про заклад.
3. Спортивні напрями.
4. Як вступити.
5. Новини.
6. Контакти.

Політика приватності та правила використання залишаються службовими сторінками, доступними з підвалу. Відомості про керівництво, команди, локації та медіа спочатку розміщуються блоками у шести основних розділах. Порожній розділ «Документи» до меню не додається.

### Новини та контент

- новини зберігаються як окремі Markdown-файли в типізованій колекції Astro;
- обов’язкові поля: заголовок, дата, короткий опис, автор або відповідальний редактор, статус публікації, обкладинка та альтернативний опис;
- кожна новина й зміна офіційного контенту проходить окремий Pull Request;
- у MVP немає CMS, бази даних, автоматичного імпорту з Google Drive, Telegram або YouTube;
- Google Drive залишається джерелом робочих оригіналів, а до репозиторію потрапляють лише погоджені й оптимізовані матеріали.

### Розгортання

- рекомендована платформа MVP — GitHub Pages;
- складання статичного сайту передбачається через GitHub Actions;
- власний домен і примусове HTTPS налаштовуються лише на окремому етапі запуску;
- до окремого дозволу workflow розгортання не створюється і Pages не вмикається;
- резервний варіант, якщо обмеження тарифу або репозиторію не дозволять Pages: окремо погоджена статична платформа без зміни архітектури сайту.

## Структура майбутнього коду

Орієнтовна структура, яку має створити наступний PR:

- `src/components/` — повторно використовувані блоки;
- `src/layouts/` — базові макети;
- `src/pages/` — сторінки й маршрути;
- `src/content/news/` — погоджені новини;
- `src/styles/` — глобальні стилі й дизайн-токени;
- `public/` — оптимізовані публічні файли;
- `tests/` — автоматизовані перевірки критичних маршрутів.

Це опис майбутньої структури, а не дозвіл створювати її в цьому PR.

## Мінімальні перевірки наступного етапу

До злиття PR із каркасом мають проходити:

- встановлення залежностей із lock-файла;
- перевірка TypeScript;
- статичне складання всіх сторінок;
- перевірка форматування або lint;
- відсутність секретів і персональних даних дітей;
- перевірка внутрішніх посилань;
- базова перевірка доступності;
- контроль розміру JavaScript і зображень.

## Цільові обмеження продуктивності

- статична генерація без серверного виконання;
- мінімальний JavaScript на публічних сторінках;
- зображення у сучасних форматах із заданими розмірами;
- відкладене завантаження зображень поза першим екраном;
- відсутність фонових відео, важких карт і рекламних трекерів;
- ціль Lighthouse перед запуском: не нижче 90 для Performance, Accessibility, Best Practices і SEO на ключових сторінках; винятки документуються.

## Безпека і приватність

- сайт не має форм реєстрації, кабінетів, платежів або бази персональних даних;
- у репозиторій не додаються секрети, токени, приватні ключі та повні непогоджені документи;
- не публікуються списки, дати народження, медичні дані або інші персональні дані вихованців;
- зовнішні вбудовування мінімізуються; карта замінюється посиланням на маршрут;
- аналітика та cookie-банер не додаються до окремого рішення.

## Наслідки

### Переваги

- швидке завантаження й просте розгортання;
- мала кількість залежностей і нижчий ризик технічних збоїв;
- зрозуміла історія погодження контенту через GitHub;
- можливість надалі додати CMS або інший хостинг без повної перебудови сторінок.

### Обмеження

- редактор без GitHub не зможе публікувати новини самостійно на першому етапі;
- кожне оновлення проходить Pull Request;
- інтерактивні сервіси й автоматизації відкладаються після запуску MVP.

## Відкладені рішення

Окремими Pull Request визначаються:

- каркас проєкту та точні версії залежностей;
- дизайн-система й візуальний прототип;
- підготовка та погодження контенту;
- workflow тестування;
- workflow розгортання;
- офіційний домен, DNS і HTTPS;
- аналітика, CMS та автоматизації після оцінки реальної потреби.
